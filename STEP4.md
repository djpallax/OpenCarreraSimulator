# OpenCarreraSimulator — Step 4 Asset Pipeline & Runtime Metrics

Step 4 replaces hard-coded geometry with a versioned offline asset pipeline and adds lightweight runtime telemetry for renderer development.

## Implemented

- All Step 3 Vulkan render foundation features
- New static `ocs::assets` engine module
- Versioned `.ocsmesh` runtime mesh format (`OCSM`, v1)
- Payload hash, bounds, vertex/index counts and structural validation
- `ocs_assetc` offline glTF/GLB compiler
- fastgltf 0.9.0 and simdjson are pinned build-tool dependencies only
- glTF scene/node transforms baked during import
- glTF -> OCS coordinate conversion
- Triangle meshes, POSITION, NORMAL and TEXCOORD_0 import
- Normal generation when source normals are absent
- 32-bit runtime indices
- Sample glTF asset compiled automatically by CMake
- Runtime mesh upload through the existing staging -> device-local path
- Vulkan GPU timestamp queries
- Runtime stats: FPS, frame time, renderer CPU time, GPU time, draw calls, triangles and mesh GPU bytes
- Optional one-Hz CSV metrics output
- Multi-terminal/tmux monitoring scripts for GPU, process CPU/RAM/I/O and engine metrics

## Coordinate contract

OpenCarreraSimulator remains right-handed:

```text
        +Z up
         |
         |
         +------ +X forward
        /
      +Y left
```

glTF source coordinates are converted once during `ocs_assetc` import:

```text
OCS.x = glTF.z
OCS.y = glTF.x
OCS.z = glTF.y
```

This cyclic permutation preserves handedness and triangle winding.

## Build

A clean configure is recommended because Step 4 adds a new engine module and an offline tool:

```bash
rm -rf build/gcc-debug
cmake --preset gcc-debug
cmake --build --preset gcc-debug
ctest --preset gcc-debug
```

The first configure needs network access for the pinned `fastgltf`/`simdjson` FetchContent dependencies, just like the test configuration already does for GoogleTest.

The build compiles:

```text
assets_src/debug/debug_wedge.gltf
        |
        v
ocs_assetc
        |
        v
build/gcc-debug/assets/debug/debug_wedge.ocsmesh
```

and the application receives that `.ocsmesh` path as its default Step 4 mesh.

## Run

```bash
./build/gcc-debug/app/OpenCarreraSimulator --gpu 0
```

Print renderer statistics once per second:

```bash
./build/gcc-debug/app/OpenCarreraSimulator --gpu 0 --stats
```

Write one-Hz metrics to `/tmp/opencarrera_metrics.csv`:

```bash
./build/gcc-debug/app/OpenCarreraSimulator --gpu 0 --metrics
```

Or choose a file:

```bash
./build/gcc-debug/app/OpenCarreraSimulator \
    --gpu 0 \
    --metrics-file ./build/opencarrera_metrics.csv
```

Load another compiled mesh:

```bash
./build/gcc-debug/app/OpenCarreraSimulator \
    --gpu 0 \
    --mesh ./my_car.ocsmesh
```

## Compile your own glTF/GLB

```bash
./build/gcc-debug/tools/assetc/ocs_assetc \
    model.glb \
    model.ocsmesh
```

`ocs_assetc` is an **offline development tool**. The simulator executable does not link fastgltf or simdjson and does not parse glTF at runtime.

Step 4 supports the geometry path needed for the next renderer milestone. Materials/textures/PBR are deliberately deferred.

## Second-monitor telemetry

Install useful Linux tools:

```bash
sudo apt install tmux nvtop sysstat lm-sensors
```

Start the simulator with engine metrics:

```bash
./build/gcc-debug/app/OpenCarreraSimulator --gpu 0 --metrics
```

In another terminal/monitor:

```bash
./scripts/monitor_runtime.sh
```

That opens a tmux dashboard containing:

- `nvtop`: GPU utilization, clocks, temperature, power and VRAM/process view where supported
- `pidstat`: OpenCarreraSimulator CPU, RSS/page faults, I/O and context-switch information
- the engine metrics CSV: FPS, frame/CPU/GPU time, draw calls and triangle count

For a focused NVIDIA hardware stream:

```bash
./scripts/monitor_nvidia.sh 0
```

The monitoring scripts are external tooling; they are intentionally not linked into the engine.

## Runtime metric meanings

- `frame_ms`: wall-clock interval between presented frames; includes vsync pacing
- `cpu_ms`: wall time spent in the renderer's current `draw_frame()` path
- `gpu_ms`: Vulkan timestamp-query duration for the recorded GPU frame
- `draw_calls`: draw submissions generated by the current test scene
- `triangles`: submitted indexed triangles
- `vertex_mib`, `index_mib`: current mesh payload sizes uploaded by this minimal renderer

These are intentionally small primitives. Later steps can extend them with upload bandwidth, resource-pool usage, physics tick time, AI time and streaming pressure.

## Runtime architecture

```text
Blender / DCC
    |
    v
 glTF / GLB                 build-time only
    |
    v
ocs_assetc ------ fastgltf + simdjson
    |
    v
 .ocsmesh
    |
    v
ocs::assets::load_mesh
    |
    v
ocs::render
    |
    +-- staging buffer
    +-- device-local vertex buffer
    +-- device-local index buffer
    `-- Vulkan draw
```

## Scope boundary

Step 4 intentionally does not implement:

- textures/KTX2
- PBR materials
- multiple runtime meshes/resources
- descriptor-set/material architecture
- mesh optimization/LOD generation
- async asset streaming
- cars/tracks/physics
- editor UI

Those build on top of the format and telemetry introduced here.
